# Архитектура и ограничения BudgetBasket

## Назначение системы

BudgetBasket поддерживает процесс бюджетирования по модулям: сотрудник создаёт заявку и плановые строки, экономист проверяет их и фиксирует результаты, администратор ведёт пользователей, модули и справочники. Статусы, права и возможность редактирования определяются backend, а не интерфейсом.

## Состав приложения

```text
Браузер
  │ HTTP
  ▼
frontend (React + Vite, :5173)
  │ REST API
  ▼
backend (FastAPI, :8000)
  ├── PostgreSQL (:5432 внутри Compose, :5433 на хосте)
  ├── SeaweedFS через S3 API (:8333)
  └── file_guard (внутренняя сеть, :8080)
        └── ClamAV
```

`frontend` отвечает только за представление и вызовы API. Бизнес-правила, авторизация, работа с заявками и вложениями находятся в `backend`. Метаданные хранятся в PostgreSQL, бинарные данные вложений — в SeaweedFS. Клиент получает файлы только через авторизованный endpoint backend и не видит внутренние ключи S3.

## Модули репозитория

| Каталог | Ответственность |
| --- | --- |
| `frontend/` | React-интерфейс, TypeScript DTO, API-клиент, страницы и компоненты |
| `backend/app/routers/` | HTTP endpoints FastAPI |
| `backend/app/services/` | Бизнес-логика, права доступа, файлы, импорт и экспорт |
| `backend/app/repositories/` | Доступ к PostgreSQL |
| `backend/alembic/` | Миграции схемы БД |
| `backend/db/init.sql` | Справочная SQL-схема; поддерживается синхронно с миграциями |
| `file_guard/` | Изолированная проверка загрузок |
| `docker-compose.yml` | Локальный стек и сетевые границы сервисов |

## Поток загрузки файла

```text
Пользователь → backend (авторизация и права) → file_guard → backend → SeaweedFS + PostgreSQL
```

До положительного результата `file_guard` объект не загружается в SeaweedFS и его метаданные не сохраняются в PostgreSQL. Backend сохраняет только байты, возвращённые `POST /internal/files/process`; исходный upload повторно не читается и не сохраняется. Если проверка отклоняет файл, API отвечает `400`; если сервис проверки недоступен или не готов — `503`.

### Безопасная обработка Excel

`.xlsx` и `.xlsm` принимаются только для формирования новой `.xlsx`-копии для просмотра. `file_guard` ограниченно проверяет исходный OOXML-архив и ClamAV, пересобирает книгу из значений и базового форматирования, затем повторяет структурную и антивирусную проверки результата. В PostgreSQL у файла сохраняются отображаемое исходное имя, фактическое `stored_name`, флаг обработки и краткий отчёт; в SeaweedFS попадает только безопасная копия.

Макросы/VBA, ActiveX, OLE и вложения, внешние связи, формулы, гиперссылки, изображения, диаграммы и другие сложные части не переносятся. Формула заменяется сохранённым значением; если его нет — неисполняемым текстом с предупреждением. Возможна потеря этих компонентов, а также части расширенного оформления. `.xls` не поддерживается: его нужно сохранить как `.xlsx`.

Пределы просмотра задаются `FILE_GUARD_EXCEL_*` (листы, строки, колонки, ячейки, объединения, длина строки и размер результата). При превышении лимитов, ошибке разбора, неготовом ClamAV или неудачной повторной проверке действует fail-closed.

## Сетевые границы Docker Compose

- Сеть `app`: frontend, backend и `file_guard`.
- Сеть `data`: backend, PostgreSQL и pgAdmin; она внутренняя.
- Сеть `storage`: backend и SeaweedFS; она внутренняя.
- `file_guard` не публикует порт на хост и не подключён к сетям PostgreSQL или SeaweedFS.

## Ограничения вложений

- Поддерживаются PDF, PNG, JPG/JPEG, XLSX и DOCX; импорт справочников принимает только XLSX.
- Максимальный размер одного файла — 25 МиБ.
- Пустые файлы и несовпадение расширения, MIME-типа и фактического содержимого отклоняются.
- PDF проверяются на повреждение, шифрование и активное содержимое.
- DOCX/XLSX проверяются как ZIP-контейнеры: блокируются макросы, path traversal, опасные внешние связи и аномальные архивы.
- PNG/JPEG полностью декодируются и ограничены по размерам изображения.
- При настройках по умолчанию `file_guard` требует доступный ClamAV; пока антивирус не готов, сервис проверки не готов к приёму файлов.

Параметры этих правил задаются переменными `FILE_GUARD_*` в `.env.example` и `docker-compose.yml`.

## Роли и граф согласования

Технические роли нормализованы таблицей `roles`; `users.id_role` хранит одну ссылку на роль. Во внешних DTO роль по-прежнему возвращается строковым полем `role`. Поддерживаются `admin`, `employee`, `economist`, `approver` и `zgd`.

Единый маршрут «Согласование бюджета организаций на 2027 год» хранится только в `steps` и `step_edges`. Отдельной сущности маршрута и связи «шаг–заявка» нет: поступление, согласование и возврат конкретной заявки на общем шаге выводятся из связанных событий `req_logs` и `step_logs`. Область шага вычисляется рекурсивно:

```text
step → непосредственные дочерние шаги → листовые steps.unit_id → requests.unit_id
```

Граф является DAG: листовой шаг принадлежит экономисту и содержит `unit_id`, промежуточный шаг принадлежит согласующему, единственный корневой шаг — ЗГД. Листовой шаг создаётся автоматически в транзакции отправки первой заявки модуля и получает закреплённого экономиста; администратор настраивает только проверяющих, ЗГД и связи графа. Backend проверяет циклы, единственный корень, роли назначенных пользователей, достижимость шагов и уникальность листового шага подразделения. Для промежуточного согласующего родительский шаг открывается после первого поступившего из дочерней ветки пакета: согласующий может сразу рассмотреть или вернуть каждую поступившую заявку, но передать шаг дальше можно только единым пакетом после поступления и согласования всех ожидаемых заявок. Для ответственного ЦФО состояние листового шага отдельно показывает ожидание ещё не отправленных заявок, как описано ниже.

Для автоматического шага ответственного ЦФО статус шага вычисляется отдельно от статуса позиции: `waiting` означает, что среди уже созданных заявок ЦФО остаётся черновик; `on_approval` — все такие заявки отправлены ответственному ЦФО; `on_revision` — позиция ожидает правок модуля или повторной проверки ответственным ЦФО после возврата экономиста; `approved` — все доступные позиции переданы экономисту. Статус группировки/позиции ЦФО при возврате равен `on_revision`, после передачи экономисту — `on_approval`.

`step_logs` хранит изменения графа и маршрутные решения, `req_logs` — историю конкретной заявки. Когда действие затрагивает заявки, обе группы записей получают общий `event_id` и создаются в одной транзакции. Для согласования, возврата и закрытия используются блокировки строк.

## Заморозка, возврат и финальная фиксация

- После завершения проверки экономистом заявка получает `frozen = true`; изменение заявки, строк и файлов блокируется.
- На этапе ответственного ЦФО строка может получить решение `approved`, `approved_with_changes` или `rejected`; принятые строки остаются `on_review` до решения экономиста, отклонённые получают `rejected`. Если отклонены все активные строки, заявка получает `rejected` и в маршрут экономиста не передаётся.
- Ответственный ЦФО может изменить фактическую сумму, подтвердить решение по строке или вернуть отдельные строки/всю доступную заявку модулю на доработку. Передача экономисту разрешается после обработки всех заявок ЦФО; при этом статус шага ответственного ЦФО становится `approved`, а статус позиции ЦФО — `on_approval`.
- Согласующий или ЗГД возвращает выбранные заявки только через непосредственный дочерний шаг и оставляет обязательный комментарий ко всей заявке.
- Возврат проходит вниз пошагово: каждый назначенный проверяющий видит свой шаг в `on_revision`, добавляет комментарий и передаёт заявку следующей дочерней ветке.
- На листовом шаге экономист явно размораживает заявку и переводит её в черновик сотрудника. После повторной отправки ветка проходит согласование заново.
- ЗГД получает заявку после передачи ему из дочернего шага и фиксирует её индивидуально. Для этой заявки все шаги маршрута считаются закрытыми, а сама заявка получает `frozen = true` и `fixed = true`; после этого данные, строки и файлы неизменяемы.

Администратор имеет технический доступ к данным и журналам, но не может согласовывать, возвращать или фиксировать бюджет. Рабочий чат доступен только сотруднику и назначенному экономисту; администратор может читать его технически, согласующие и ЗГД к чату не допускаются.

## Инженерные ограничения

- PostgreSQL — единственный runtime-источник реляционных данных; локальные JSON-файлы не используются как база данных.
- SeaweedFS используется только через S3-совместимый API; внутренние сервисные порты не используются в прикладном коде.
- Новые изменения схемы требуют согласованного обновления ORM-моделей, миграций Alembic и `backend/db/init.sql`.
- Пароли не хранятся в открытом виде.
- Новые переменные окружения должны быть добавлены в `.env.example`.
- В production необходимо заменить локальные учётные данные и ограничить доступ к опубликованным портам.
